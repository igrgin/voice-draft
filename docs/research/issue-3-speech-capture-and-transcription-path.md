# Research: speech capture and transcription path

Date: 2026-07-08

Issue: [#3 Choose speech capture and transcription path](https://github.com/igrgin/voice-draft/issues/3)

## Question

How should the application capture voice in the React frontend and turn it into raw text: browser MediaRecorder plus backend upload, Web Speech API, direct provider upload, streaming transcription, or another path? Compare browser support, privacy/security implications, server responsibilities, latency, and how well each path fits a Spring Boot backend.

## Recommendation

Start with **browser `getUserMedia()` + `MediaRecorder` in React, upload the recorded audio blob to Spring Boot as multipart form data, and run transcription server-side through Spring AI's OpenAI transcription support**. `getUserMedia()` is a secure-context browser API that prompts for microphone permission, `MediaRecorder` is a standard recording API for `MediaStream`, Spring Boot is documented for multipart uploads, and Spring AI provides Spring Boot auto-configuration for OpenAI transcription. [MDN `getUserMedia()`](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), [MediaStream Recording spec](https://w3c.github.io/mediacapture-record/), [Spring uploading files guide](https://spring.io/guides/gs/uploading-files/), [Spring AI OpenAI Transcriptions](https://docs.spring.io/spring-ai/reference/api/audio/transcriptions/openai-transcriptions.html)

Use Web Speech API only as an optional enhancement or prototype path, not the primary path, because MDN marks `SpeechRecognition` as not Baseline and the Web Speech spec leaves recognition implementation local-or-remote unless `processLocally` is required and available. [MDN `SpeechRecognition`](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition), [Web Speech API spec](https://webaudio.github.io/web-speech-api/)

Defer realtime transcription until the product needs live captions, voice-agent interaction, or visible partial transcript deltas. OpenAI's own audio docs separate request-based file APIs for bounded requests from realtime sessions for low-latency live audio, and realtime transcription emits transcript deltas as audio arrives. [OpenAI audio guide](https://developers.openai.com/api/docs/guides/audio), [OpenAI realtime transcription](https://developers.openai.com/api/docs/guides/realtime-transcription)

Do not send app-owned standard provider API keys from the browser. OpenAI's API reference says API keys are secrets and should not be exposed in client-side code; if a browser connects directly to OpenAI Realtime, the backend must create an ephemeral token or initialize the session with the standard key server-side. [OpenAI API authentication](https://developers.openai.com/api/reference/overview), [OpenAI Realtime WebRTC](https://developers.openai.com/api/docs/guides/realtime-webrtc)

## Browser Support Notes

`navigator.mediaDevices.getUserMedia()` is Baseline widely available, available only in secure contexts, and prompts the user for permission to use media input. [MDN `getUserMedia()`](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)

MDN browser-compat-data lists `MediaDevices.getUserMedia()` support in Chrome 53, Edge 12, Firefox 36, Safari 11, Samsung Internet 6.0, and Android WebView 53; that makes microphone capture a reasonable cross-browser baseline for a modern React app. [MDN BCD `MediaDevices.getUserMedia`](https://github.com/mdn/browser-compat-data/blob/main/api/MediaDevices.json)

`MediaRecorder` is Baseline widely available, and MDN browser-compat-data lists `MediaRecorder` support in Chrome 47, Firefox 25, Safari 14.1, iOS Safari 14, Opera 36, and mirrored Chromium-derived browsers. [MDN `MediaRecorder`](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder), [MDN BCD `MediaRecorder`](https://github.com/mdn/browser-compat-data/blob/main/api/MediaRecorder.json)

The MediaStream Recording spec exposes `MediaRecorder.isTypeSupported(type)` and allows the user agent to choose or reject container/codec configurations, so the frontend should probe MIME types instead of assuming one container everywhere. [MediaStream Recording spec](https://w3c.github.io/mediacapture-record/#dom-mediarecorder-istypesupported)

`SpeechRecognition` is not Baseline according to MDN; MDN browser-compat-data records a mix of prefixed Chrome/Safari support and Firefox support gated behind `media.webspeech.recognition.enable`, so it should not be the app's only transcription path. [MDN `SpeechRecognition`](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition), [MDN BCD `SpeechRecognition`](https://github.com/mdn/browser-compat-data/blob/main/api/SpeechRecognition.json)

## Privacy and Security Implications

Microphone capture exposes personally identifiable information, and the Media Capture and Streams spec requires explicit user consent before sharing microphone/camera data with an application. [Media Capture privacy/security](https://w3c.github.io/mediacapture-main/#privacy-and-security-considerations)

The same spec requires user-visible indication when camera or microphone access changes and encourages ongoing indication while devices are live, so the frontend should stop tracks promptly after recording and show app-level recording state that matches browser state. [Media Capture privacy indicator requirements](https://w3c.github.io/mediacapture-main/#privacy-indicator-requirements)

OpenAI publishes endpoint-level data controls and regional storage/processing tables that include `/v1/audio/transcriptions` and `/v1/realtime`, so the app's privacy copy should name the selected provider endpoint and its current data-control posture at implementation time. [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data)

Those OpenAI data-control details are provider-specific, so the backend path should keep provider selection and consent copy explicit rather than relying on browser-owned Web Speech behavior. [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data), [Web Speech API spec](https://webaudio.github.io/web-speech-api/)

The Web Speech API spec requires explicit informed consent and an obvious recording indication, but it is agnostic to whether recognition is server-based or embedded, and `processLocally=false` lets the user agent choose local or remote recognition. [Web Speech API spec](https://webaudio.github.io/web-speech-api/)

OpenAI says standard API keys are secrets that should not be shared or exposed in browser/app client-side code, so direct browser transcription with a standard key is not an acceptable production architecture. [OpenAI API authentication](https://developers.openai.com/api/reference/overview)

## Backend Responsibilities

For the recommended baseline, Spring Boot should expose one authenticated multipart endpoint that receives the audio blob, checks the declared MIME type against the MIME type actually selected by `MediaRecorder`, enforces size/duration policy, calls transcription, and returns plain raw text. Spring's upload guide documents a Spring Boot app that accepts multipart file uploads, and `MultipartFile` documents that uploaded content may live in memory or temp disk and is cleared at request end unless copied. [Spring uploading files guide](https://spring.io/guides/gs/uploading-files/), [Spring `MultipartFile`](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/multipart/MultipartFile.html), [MediaStream Recording spec](https://w3c.github.io/mediacapture-record/)

Spring AI's OpenAI transcription support fits that server role: it provides Spring Boot auto-configuration via `spring-ai-starter-model-openai`, uses `spring.ai.openai.api-key` or transcription-specific API-key properties, and exposes `AudioTranscriptionPrompt`/`AudioTranscriptionResponse` model calls. [Spring AI OpenAI Transcriptions](https://docs.spring.io/spring-ai/reference/api/audio/transcriptions/openai-transcriptions.html)

If realtime becomes necessary, Spring Boot can still own credentials and session policy, but the backend shape changes from a simple REST upload to either token/session brokering for browser WebRTC or WebSocket message handling for backend-mediated streams. [OpenAI Realtime WebRTC](https://developers.openai.com/api/docs/guides/realtime-webrtc), [Spring WebSockets](https://docs.spring.io/spring-framework/reference/web/websocket.html)

## Latency Implications

Request-based transcription is simplest for bounded recordings: OpenAI says the speech-to-text guide is for file uploads and bounded audio requests, and directs applications that need live transcript deltas from a microphone or media stream to realtime transcription. [OpenAI speech to text](https://developers.openai.com/api/docs/guides/speech-to-text)

Realtime transcription is the low-latency path because OpenAI says it streams transcript deltas as audio arrives, uses `gpt-realtime-whisper` for live audio, and exposes delay settings that trade transcript quality against latency. [OpenAI realtime transcription](https://developers.openai.com/api/docs/guides/realtime-transcription)

The first product path should accept request-response latency unless the UI requires live captions or partial text while the user is still speaking, because OpenAI states that lower latency requires a realtime connection, more careful audio handling, and a session model that can emit partial events. [OpenAI audio guide](https://developers.openai.com/api/docs/guides/audio)

## Decision

Build the first implementation as:

1. React asks for microphone access with `navigator.mediaDevices.getUserMedia({ audio: true })`. [MDN `getUserMedia()`](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)
2. React selects a supported recording MIME type with `MediaRecorder.isTypeSupported(...)`, records audio with `MediaRecorder`, and uploads the resulting `Blob` as multipart form data. [MediaStream Recording spec](https://w3c.github.io/mediacapture-record/), [MDN `MediaRecorder`](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder)
3. Spring Boot receives the file as multipart data, keeps provider API keys server-side, and calls Spring AI's OpenAI transcription model. [Spring uploading files guide](https://spring.io/guides/gs/uploading-files/), [OpenAI API authentication](https://developers.openai.com/api/reference/overview), [Spring AI OpenAI Transcriptions](https://docs.spring.io/spring-ai/reference/api/audio/transcriptions/openai-transcriptions.html)
4. The backend returns raw text and optional metadata; realtime transcript deltas remain a later decision for live-caption or voice-agent UX. [OpenAI speech to text](https://developers.openai.com/api/docs/guides/speech-to-text), [OpenAI realtime transcription](https://developers.openai.com/api/docs/guides/realtime-transcription)
